一键初始化 Hermes：新用户免配置免学习直接上手，老用户自动增量、零副作用。

---

## 这是什么

一份**开箱即用的 Hermes 初始化方案**。它解决一个真实痛点：Hermes 装好后默认是个**能力很强但完全不认识你**的"陌生外包"——不知道你的生意、你的标准、你的雷区，会礼貌敷衍、编数据、等你指令。

这套方案让 Hermes 在**首次对话时**就完成对你的画像，把它从"陌生人"变成"懂你、替你扛活、敢反驳你"的 AI Agent 合伙人。

## 它为什么不一样

市面上很多"AI 配置"只是给你调几个参数。这套方案给 Hermes 注入的是一套**工作方式**——

- **持续记忆**：分层存、写事实不写命令、关键状态落盘不靠聊天记——它真的记得你，越用越懂你
- **工作纪律**：带证据干活、改动必回归、打了"✅"必核销到代码行、一次只改一条——不编数据、不糊弄
- **自动化机制**：反复的活自动跑，你只做判断不当操作员；而且自动≠静默，跑完必汇报、你随时能把关
- **自主进化**：升级走增量合并、只补不覆盖、绝不破坏你的已有配置——越用越好，但不越界不乱来

## 它是活的样板，不是空谈

这个项目的运营、维护、升级、迭代，全部由 AI Agent 在执行落地——使用者给方向和判断，AI 负责实现、运营、持续进化。**它想教你的"让 Agent 自主进化"，它自己就是这么做的。**（截至 v4.12，方法论同步、自动检测、版本迭代均已在自动机制上运行）

## 两个文件

| 文件 | 给谁 | 作用 |
|------|------|------|
| `hermes_onboarding_guide.md` | Hermes 执行 | 一键初始化的完整执行脚本（Q1~Q9 + 写入映射 + 规则） |
| `hermes_onboarding_methodology.md` | 给人看 | 方法论说明，讲清楚"为什么这么做" |

## 核心特性

- **新用户**：完整初始化，零配置零学习直接上手
- **老用户**：自动增量升级，只补缺的字段，**不重走、不动已有配置**（零副作用）
- **版本机制**：统一版本自适应，后续升级喂新版即增量

- v4.32（2026-09-18）｜ 更新日期：2026-09-18

### v4.32 更新说明（外部执行链路的失败分层与重试纪律 · 验证告警别往生产通道推测试消息）

- **外部命令/执行链路失败先分层再处理，只对连接层瞬时闪断自动重试**：远程/外部执行（SSH、HTTP、API 调用等）失败先判定失败层——连接层瞬时闪断（如 `Connection closed`/`Connection reset`/`kex_exchange_identification`，TCP 握手期被对端 reset 的典型瞬时抖动，rc=255）才自动重试（最多 2-3 次、退避）；认证失败（rc=5 Permission denied）和业务错误码绝不重试，否则在错误场景白空转。重试安全的先决条件 = 目标端幂等对齐（执行端先读当前状态、已生效则 SKIP，重试不会重复操作）。诊断顺序：先看 rc 和 stderr——rc=255+连接断 = 执行通道问题（重试兜底），rc=0 但没生效 = 内容/逻辑问题。进 guide「④ 运维纪律」+ methodology 长期进化。
- **验证告警/通知路径时，别往真实生产通道推测试消息**：为验证告警逻辑故意触发一条测试告警，会让使用者误以为生产真的出事故——验证要么加明确 TEST 前缀、要么指向测试 webhook/仅 print 不真推，绝不让生产告警通道出现非真实消息；若已误推，第一时间明确"那是测试消息，实际状态正常"并给出真源状态对比。进 guide「④ 运维纪律」+ methodology 长期进化。
- 来源：broker-bridge 技能实战血训（SSH 连接层瞬时闪断重试 / 验证告警误推假告警），两条均抽象为可脱离项目复用的通用纪律，两处同步。

### v4.31 更新说明（三条工程运维/验证纪律：期望值漂移、控制流反转、缓存新鲜度）

- **黄金测试/校验脚本的硬编码期望值会随基线变更而过时**：改被测系统基线（改池/改口径/改成本/改引擎）后，验证脚本里写死的期望值不会自动跟上，会永远误报 FAIL——改基线后要同步重跑验证脚本拿当前真实值更新期望值。进 guide「① 验证纪律」+ methodology 长期进化。
- **有独立兜底的环节不该当硬门卡死后续**（管线控制流反转）：流程里某个环节若已有独立兜底能单点补齐，它就不是致命门——把它当硬门退出会卡死后面没有兜底的环节，出现"部分数据齐、部分旧"的混合态；排查"数据部分更新"要分环节分别查健康。进 guide「② 工具与调试纪律」+ methodology 长期进化。
- **懒加载/静态缓存读外部数据必须带数据新鲜度失效键**：服务缓存外部数据时，若只在"缓存空"时填充、不带数据日期失效键，服务在数据更新前启动/加载一次就会永远用旧值。缓存必须带 asof（数据日期）。进 guide「④ 运维纪律」+ methodology 长期进化。
- 来源：etf-momentum-dashboard 技能实战血训（verify 期望值漂移 / monitor 与主链控制流反转 / movers 评分缓存永不失效），三条均抽象为可脱离项目复用的通用纪律，两处同步。

### v4.29 更新说明（对比评测 A/B 可信度纪律）

- **对比评测（A/B）可信度纪律**：做模型/工具/配置横向对比时——①ground truth 用真实执行生成（标准答案用真实程序跑出来），**永远不信被测对象自报的"已实测验证"**（它可能是心理执行还谎称跑过）；②判分基准的 print 结构必须=题目结构（同一段代码一次性打印 vs 串行打印答案不同）；③跨条件对比必须同一网络位置、同 prompt、同参数测，否则网络路径/时段差异污染结论；④严谨 A/B 用交错执行 + 报中位数/标准差，不看单次均值。方向稳定当定性用，幅度别当精确值。来源：hermes-china-llm-providers 技能实战血训，进 guide「① 验证纪律」+ methodology 长期进化，两处同步。

### v4.28 更新说明（保守半自动：判断可自动化，写入/发布留人工）

### v4.26 更新说明（检测器输出签名与 agent prompt 是两向契约，改签名同一次编辑教给 prompt）

- **检测器的输出签名与被唤醒 agent 的 prompt 是两向契约**：当你给 monitor 检测器扩展一个新的变更签名（如新增 CHANGED_SOUL: 与既有 CHANGED: 并列）时，必须在同一次编辑里教会 cron/agent prompt 这个新签名（它什么意思、怎么判断、何时 SILENT）。检测器→prompt 的握手是协议：检测器能发出的每一种签名，prompt 里都必须有对应的解释分支，否则 agent 拿到看不懂的新信号会误处理（或静默丢弃）。改完 prompt 后，用 grep 对照检测器能发出的每个签名逐一确认 prompt 里都有覆盖。来源：cron-job-reliability 技能实战血训（2026-09-17），进 guide「④-1 执行机制自动化」+ methodology，两处同步。

- **检测器的扫描范围要和实际写入目标对齐**：只保证"被扫描文件内部的元数据新鲜度"还不够——还要确认**扫描树本身覆盖了你实际编辑的所有文件**（如 `SOUL.md`/`config.yaml`/根级 persona 文件在 skills 树之外，只扫 `~/.hermes/skills/` 的检测器会静默漏掉它们）。把规则移到更强的强制点（如 SOUL.md）却落在监控扫描树之外，是回归不是修复——改完必须重审监控扫描目录是否还包含那个写入目标。来源：cron-job-reliability 技能实战血训（2026-09-17），进 guide「④-1 执行机制自动化」+ methodology，两处同步。

### v4.23 更新说明（涉及某系统先加载专项 skill 再谈 · 禁止脑补系统逻辑）

- **涉及某系统先加载该系统专项 skill 再谈**：谈某个已有系统的结论/建议前，先加载该系统对应的专项 skill、掌握它的真实逻辑（选股/买卖/监控怎么跑）再开口，禁止凭记忆或压缩摘要推断系统逻辑。上下文重置后第一动作是扫技能库、加载相关 skill、读系统真源，才动手/才给结论——与"禁止脑补用户画像"同构，是它的镜像（不许脑补系统逻辑）。血训：上下文重置后没加载动量系统专项 skill，凭印象给了"油气65%+黄金35%"资产配置建议，跟系统实际逻辑对着干，被连续追问三次点破。

### v4.22 更新说明（检测器判断变更不能只靠元数据文件）

- **检测器判断变更不能只靠元数据文件，要交叉核对真实文件 mtime**：变化检测器如果只比对元数据文件（如 skill 的 `.usage.json` 里的 `last_patched_at`）会漏报——**不是所有写路径都会更新元数据**（如直接用 `patch` 工具改 SKILL.md 不会更新 `.usage.json`，元数据时间戳停在旧值，检测器误判 NO_CHANGE，变更永远到不了同步链）。判定"有没有变"以**真实文件 mtime 为地基**：取（元数据时间戳, 文件 mtime）两者较新者比对 `last_scan_at`。任何依赖元数据文件的检测器，其可靠性只到"所有写路径都更新该文件"为止——要审计写路径，不只审计读路径；改完用正向测试（touch 文件但不碰元数据→必须检测到 CHANGED）+ 负向测试（重跑无误报）双验。
- 来源：cron-job-reliability 技能实战血训（2026-09-17），进 guide「④-1 执行机制自动化·检测器」+ methodology 长期进化，两处同步。

### v4.21 更新说明（monitor 类 job 高频 tick · 调度血训）

- **monitor 类 job 的调度要用高频 tick，别设每天单点**：变更才唤醒 agent 的检测型任务，调度频率要够高（如每 30 分钟）。每天单点有两个致命问题——①单点脆弱：某天 tick 恰好落在 cron 空窗就漏检整天，且 monitor 静默、执行记录看不到"被跳过"，故障不可见；②时滞最长 24 小时：白天改的 skill/配置要等到晚上才检测，违背"变更即审视"。高频 tick 让变更最多一个周期就被唤醒，漏一个下个周期自动补上。

### v4.11 更新说明（定时唤醒原则 · cron 与 monitor 的选择）

- **新增「定时唤醒原则」**（④-1 执行机制自动化 子规则）：**纯定时提醒用 cron**（到点发消息即可，不需要 Hermes 干活）；**需要唤醒 Hermes 执行的用 monitor**（monitor 检测到变化/条件满足才唤醒 agent 处理，人工零干预，任务完成汇报）。
- **判断标准**：任务只是"到点提醒一下"→ cron；任务需要 Hermes 判断/执行/处理 → monitor。**别把要干活的定时任务建成纯提醒**（断链：触发了但没人执行），**也别把纯提醒建成 monitor**（白烧 token 唤醒 agent 却没活干）。
- 这是"执行机制自动化"的落地决策规则：选对 cron/monitor，才让机制真正自动化且不费 token。

### v4.10 更新说明（核心工作原则 · 执行机制自动化不靠记忆）

- **新增深度协作愿景 4c「执行机制自动化，不靠记忆」**（核心工作原则）：反复要做的活落成自动机制（定时任务/cron/脚本），到点自己跑，不依赖使用者记得触发、不依赖 Hermes 临时想起来；**使用者的角色是判断确认，不是操作执行**——机制自动跑、有结果汇报给使用者判断；机制能扛的自动化扛，人只做机器做不了的判断；完成后汇报不闷头跑（自动化≠静默，是"自动执行+明确汇报"）。

- **检测脚本**：`scripts/check_update.py` 三层退化检测（releases→tags→README 版本号），只读零副作用。
